# 镜像构建

为当前项目创建、审查或改进 Dockerfile，按用户请求设计方案或实施改动。范围包括直接影响镜像构建和运行的忽略规则、构建入口及配套配置。

## 原则

- **用途明确**：区分开发、测试和生产用途，从实际调用入口确认构建上下文、Dockerfile、目标阶段及运行方式。根据用途决定保留哪些工具、资源和权限。
- **遵循工具链**：查阅与项目所用工具及版本相符的官方容器构建建议，如 [Docker](https://docs.docker.com/build/building/best-practices/)、[pnpm](https://pnpm.io/docker) 和 [Turborepo](https://turborepo.dev/docs/guides/tools/docker)。沿用项目的版本与锁文件约定，复用既有构建和打包入口，按需采用工具原生的依赖裁剪与交付机制。由工具链维护依赖关系，避免手工拼装依赖目录或依赖其内部布局。
- **配置简明**：按需使用构建参数和环境变量，固定且仅在局部使用的值就近写明。保留工具原生的配置方式和需要统一维护的共用值，避免层层转发或重复定义。区分构建输入与运行配置，临时设置只在所需步骤或阶段内生效。
- **交付精简**：构建上下文只纳入所需输入。区分构建和运行所需的内容，合理划分阶段，只交付必要的程序、依赖和资源，并核对原生依赖与运行环境是否兼容。选择基础镜像时，先保证交付完整可用，不以阶段或层的数量为优化目标。
- **缓存有效**：按输入的变化频率安排步骤，保留完整的安装与构建输入。优先使用工具原生缓存，区分镜像层缓存、依赖下载缓存与任务结果缓存，核对实际缓存路径，以及本地和持续集成如何保存与恢复缓存。减少重复下载与计算，确保相关输入变化时缓存失效，缓存缺失时仍能重建。
- **运行约定**：明确最终进程的身份、工作目录、可写路径及挂载权限，区分初始化所需权限与应用运行权限。能够无特权运行的服务使用非 root 身份；检查入口脚本和运行配置中的覆盖设置，核对实际启动命令、信号处理与退出行为。
- **实际验证**：通过正式入口构建，并以预期身份、在预期挂载条件下运行最终镜像。本地与持续集成复用相同构建定义，通过显式配置处理环境差异。根据本轮改动选择验证范围，检查实际运行行为，明确哪些结论已验证、哪些尚未验证。

## 改进既有镜像

沿现有构建和启动流程定位问题，保留用途所需的工具和有效行为，根据实际问题确定改动边界。新路径接管后，移除已被替代的重复实现。

优化体积或构建速度时，先检查镜像内容和耗时环节，改动后在相同条件下复测；涉及缓存时，区分首次构建与复用缓存的结果。验证时复用项目已有入口，验证规模与改动风险相称。
