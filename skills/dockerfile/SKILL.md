# 镜像构建

为当前项目创建、审查或改进 Dockerfile，按用户请求提供设计或实施。范围包括直接影响镜像构建和运行的忽略规则、构建入口及配套配置。

## 原则

- **用途明确**：区分开发、测试和生产用途，沿实际调用入口确认构建上下文、Dockerfile、目标阶段及运行方式。根据用途决定需要保留的工具、资源和权限。
- **遵循工具链**：查阅与项目工具及版本相符的官方容器构建建议，如 [Docker](https://docs.docker.com/build/building/best-practices/)、[pnpm](https://pnpm.io/docker) 和 [Turborepo](https://turborepo.dev/docs/guides/tools/docker)。沿用项目的版本与锁文件约定，复用既有构建和打包入口，按需采用工具原生的依赖裁剪与交付机制。依赖关系由工具链维护，避免手工拼装依赖目录或依赖其内部布局。
- **交付精简**：控制构建上下文，仅纳入所需输入。按用途区分构建所需与运行所需内容，通过合适的阶段边界只交付必要的程序、依赖和资源，并核对原生依赖与运行环境的兼容性。以完整可用的交付为前提选择基础镜像，阶段或层的数量不作为优化目标。
- **缓存有效**：按输入的变化频率安排步骤，保留完整的安装与构建输入。优先使用工具原生缓存，区分镜像层缓存、依赖下载缓存与任务结果缓存，核对实际缓存路径及其在本地和持续集成中的保存与恢复方式。减少重复下载与计算，确保相关输入变化时正确失效，缓存缺失时仍能重建。
- **运行约定**：明确最终进程身份、工作目录、可写路径及挂载权限，区分必要的初始化权限与应用运行权限。能够无特权运行的服务使用非 root 身份；结合入口脚本和运行配置的覆盖，核对实际启动命令、信号处理与退出行为。
- **实际验证**：通过正式入口构建，并在预期身份和挂载条件下运行最终镜像。本地与持续集成复用相同构建定义，环境差异显式配置。根据本轮改动选择验证范围，检查实际运行行为，区分已验证与未验证的结论。

## 改进既有镜像

沿现有构建和启动链定位问题，保留用途所需的工具和有效行为，根据实际问题确定改动边界。新路径接管后，移除已替代的重复实现。

优化体积或构建速度时，先观察镜像内容和耗时来源，再在相同条件下复测；涉及缓存时，区分首次构建与缓存复用的结果。验证复用项目已有入口，规模与改动风险相称。
