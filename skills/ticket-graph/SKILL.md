# 票图管理

工具维护票据的状态和依赖，检查结构并提供查询与变更历史。它不推荐下一张票，也不决定实施顺序或交付是否完成。

## 接入

用户明确启用选定票集后使用。将配置位置和工具入口记入项目既有票据约定，后续会话沿用该范围。

用 `node` 运行本技能目录下的 `scripts/ticket-graph.mjs`，先通过 `--help` 查看命令、票据格式和输出约定。取得完整技能目录并具备 Node.js 即可使用，无需安装依赖。

首次使用 `init` 创建配置，已有配置直接沿用。通过 `--config` 显式选择票集；票目录和完成值按项目约定配置。交付完成表示本票约定的交付已具备，后继票可以据此继续实施。

配置可直接编辑，格式见[配置结构定义](ticket-graph.schema.json)。`init` 只创建配置，使用 `check` 检查票图结构。

## 工作判断

调用者依据原始需求和实际证据决定工作范围、优先级、派发与验收。工具的检查限于声明的结构，无法判断需求是否覆盖、依赖是否遗漏或交付是否属实。

- `unblocked` 筛选自身未完成、已登记的直接前置票均被标记完成的票。这些前沿票不代表推荐顺序，也不限定可开展的工作范围。
- 前置尚未满足的票，也可以推进不依赖缺失交付的独立部分；需要该交付的部分仍须等待。
- 发现已标记完成的票仍有本票约定内的工作未完成时，通过工具改回项目适用的未完成状态，并核对受影响的后继票。状态按事实修正，工具不规定固定的流转顺序。

## 数据维护

各票文件是当前数据的唯一依据。`status` 和 `blocked_by` 保存在 YAML 文件头，正文自由编写。创建票时可直接写入初值，此后的状态和依赖变更通过工具完成。保持票标识稳定；同票的正文编辑与命令写入错开，并保留机器字段。

字段损坏导致工具无法读取时，先做保留原值的最小格式修复，再检查。结构问题可逐票修复；一次修改成功不表示其他问题也已解决。历史只记录通过工具完成的变更，供追溯使用，不参与当前状态计算。

命令失败时，先核对错误和已写入的内容，再决定下一步；写入结果不确定时先查明实际状态。查询失败不能当作没有待办工作。
