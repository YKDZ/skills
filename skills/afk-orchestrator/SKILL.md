你只负责编排、验收与升级决策。实现和独立审查交给隔离上下文中的 subagent；主上下文维护权威来源、验收合同、固定点、预算和阶段状态。

## 输入与授权

用户提供一组 ticket 与对应 Spec。已批准的 Spec 与 `ready-for-agent` ticket 授权范围内的本地实现和非破坏性验证。原始材料已有明确结论时，不再请求用户重复确认。

以下情况交回主 agent 判断；需要新增权限时再询问用户：

- 实质改变既定范围、接口、生产语义或验收标准
- 写入外部系统、执行破坏性操作或产生新的显著成本
- 权威材料互相冲突，且无法保守实施

遇到 `ready-for-human` ticket 时停止续派，记录 `INCOMPLETE` 并整理人类工作指引。暂停与恢复交给用户或运行环境。

## 主流程

1. 按依赖、生产边界与写入范围拆成纵向切片；一个切片交付一个可观察结果。若整个变更能在一个有界会话内完成，不为追求形式继续拆 ticket
2. 为切片建立固定点、验收合同、风险档位、模型 tier、可写范围、预算和门禁安排。验收标准必须对应一个能在基线失败的反例或可证伪观察；已经通过且没有区分力的标准不能充当完成证据
3. A 直接实施；B 在实施消息中给出机制简案；C 先派机制级设计切片，设计被接受后再派实施。不要为每个 ticket 重复一份相同设计
4. 按 [消息构造参考](references/delegation-messages.md) 使用当前宿主可用的隔离上下文机制派发。实现调用 `afk-slice-worker`；审查调用 `afk-slice-reviewer`
5. 实施者提交 `READY_FOR_ACCEPTANCE` 后，编排者逐项核对合同，物化不含范围外修改的候选提交，再按风险路由独立审查
6. blocker 触发一次有界返工和一次 closure check；设计假设被推翻时退出返工循环，转设计事件或重新切片
7. 合同、约定审查和门禁收敛后记录 `ACCEPTED`。所有切片完成后只审计跨切片接缝、共享不变量和 held-out 生产边界，并在最后一次整合后运行根门禁

## 验收合同

从 ticket、Spec、ADR、已接受的设计文档与其他权威材料提取证明义务：

```text
ID / 权威来源 / 要求或不变量 / 生产接缝或反例 / 状态与证据
```

A 类可内联合同；包含多项证据、使用宿主持久任务机制或跨切片共享设计的工作保留独立记录。合同规定结果与证明义务，不规定可逆的局部实现方法。

`READY_FOR_ACCEPTANCE` 只表示候选证据齐全。测试绿色、提交存在、finding 已关闭或持久任务状态已完成均不能单独关闭合同条目。独立审查寻找遗漏的反例，不能代替编排者逐项核对。

## 风险与模型路由

风险由残余不确定性、失败影响和不可逆性决定，不由工作阶段或技术关键词单独决定。

| 路由 | 判据 | 前置设计 | 实现 tier | 审查 tier |
| --- | --- | --- | --- | --- |
| A 有界 | 有既有模式；失败空间有界；可由稳定测试表达；局部且易回滚 | 无 | t0 | 不做逐切片模型审查；运行确定性门禁 |
| B 新接缝 | 范围清晰；引入新接缝或跨包机制；关键失败模式仍可列举 | 内联机制简案 | t1 | 一名 contract reviewer：t1 |
| C 开放 | ownership、状态转移、崩溃恢复、权限或外部系统语义尚未关闭；错误代价高或难回滚 | 共享机制设计文档，必要时一次性原型 | 设计：t2；设计接受后的实现：t1 | contract：t1；failure：t2，两个隔离上下文 |

模型标识、思考强度、同 tier 候选选择与 fallback 全部由项目 `AGENTS.md` 声明。本技能只引用 t0/t1/t2，不重复模型配置，也不从宿主产品名、编排者配置或可用模型列表自行推断。项目使用不同 tier 名称时，`AGENTS.md` 必须给出等价映射；没有可执行映射时，在派发前报告 `INCOMPLETE`。

例行编排与记账不要求 t2。只有路由争议涉及不可逆设计、权威材料冲突或 C 类设计裁决时，才单独派 t2 决策切片。

实施失败本身不自动升级。只有新证据表明测试接缝失真、机制假设错误、范围跨越新生产边界或失败空间不再有界时，A→B 或 B→C。升级产生设计事件；不得在返工消息里隐式补设计。

C 类设计派发必须明确原型许可：`不允许`，或 `允许一个`并给出不确定性范围、可写范围和独立 active-time 预算。未写许可视为不允许。执行前，design worker 必须记录单一可证伪假设、反证观察、判定阈值、将解锁的设计决策和停止条件；不能用“探索一下”作为目标。同一设计切片最多一个原型；结果不确定、预算耗尽或出现第二个假设时报告 `INCOMPLETE`，不得自行扩张。

## 预算与会话

用户指定预算时优先服从。未指定时使用以下 active-time 护栏；queue、外部系统与人工等待单独计时：

- A：实现 30 分钟，最多一个实现会话；不做开放式续派，明确的瞬时工具失败可重试一次
- B：实现 90 分钟，最多一次带证据目标的续派
- C：设计 60 分钟、实现 120 分钟，各最多一次带证据目标的续派
- 单次 review 或 closure：45 分钟

到达护栏时要求 checkpoint：报告 `INCOMPLETE`、已形成证据、未决假设和最小下一步。护栏不是把未证明事项判为完成。持久任务的用量预算只在用户明确要求且宿主支持时设置。

- 新切片、设计、初审与 closure 都使用宿主能提供的隔离上下文：不注入主会话历史，不继承前一位 agent 的结论，只接收自包含任务契约和事实指针。具体工具与参数由宿主决定，本技能不作假设
- 宿主无法提供独立上下文时，记录隔离能力缺失；该次审查不得宣称独立。B/C 必需的独立审查无法替代时，阶段保持 `INCOMPLETE`
- 消息必须自包含任务契约，但事实材料通过路径与提交指针提供，不复制完整文档或历史讨论
- 只有同一原子目标仍在推进且能指定下一项证据增量时才复用会话；连续两次没有新变更、新 RED/GREEN 或被排除假设时停止
- 实现与审查使用不同会话；审查者不继承实现者的完成结论

## 并行与写入所有权

只有无顺序依赖且写入范围不重叠的切片可以并行。一个工作树同时只有一个写入者；重叠写入串行，独立分支可使用 `git worktree`。审查者只读。C 类双审可以并行，但必须使用彼此隔离的上下文并读取相同的不可变候选。

## 审查与收敛

A 类不做逐切片模型审查；最终审计可按集成风险抽样。B 类做一次 t1 contract review。C 类做相互独立的 t1 contract review 与 t2 failure review。不要调用上游 `code-review` 代替这些模式；它的 Standards/Spec 固定双轴不等同于这里的风险审查。

只有 `BLOCKER` 阻塞接受。BLOCKER 必须同时满足：

- 属于当前变更引入、恶化或 Spec 明确纳入的范围
- 有可执行反例，或基于当前代码与可达输入的具体因果链
- 违反验收合同、已接受不变量或明确生产边界
- 会造成实质正确性、安全、数据或用户影响

风格、重复、可维护性偏好、投机性 hardening、范围外历史债务均为 `NONBLOCKING`。它们进入观察或 backlog，不在最终审计中自动复活。没有开放 BLOCKER 即可收敛；“零 finding”不是接受目标。

初审发现 BLOCKER 后：

1. 接受或拒绝 finding 并记录理由；只把接受的 blocker 加入合同
2. 派一次有界返工
3. 派一个新的 t1 closure reviewer，只核验已接受 blocker、受影响合同和返工引入的回归；不重新做开放式 smell 搜索

closure 只有在原 blocker 未关闭，或返工新引入了可证明的合同/不变量违例时才能阻塞。closure 后仍有 blocker 则停止逐项循环，在设计事件、重新切片与 `INCOMPLETE` 之间裁决。

finding 推翻设计假设、共享不变量或 ownership/状态机制时，立即标记 `DESIGN_EVENT`，不计作普通实现返工。同类问题只有在生产接缝上的 invariant oracle 确实覆盖该反例后才视为机制性关闭；“新增了一个测试”本身不充分。

问题记录使用：

```text
ID / BLOCKER|NONBLOCKING / 模式 / 合同 ID / 固定点 / 因果反例 / 范围类别 / 状态 / 关闭证据
```

## 门禁与最终审计

- 实现与返工运行切片级测试、类型检查和生产边界验证
- 根门禁只在整合里程碑、共享基础设施变化或最终候选上运行；最后一次整合后的成功根门禁可同时充当最终门禁，不重复执行
- 发布产物、真实权限、真实认证、跨进程或恢复语义必须从相应生产入口证明，helper-level GREEN 不充分
- 最终审计只覆盖跨切片接缝、共享不变量、未在切片层证明的 held-out 边界和整合回归；非 C 风险使用 t1，存在 C 类开放审计面才使用 t2

## 完成与记录

证据齐全时实施者报告 `READY_FOR_ACCEPTANCE`；只有合同、约定审查和门禁均收敛后，编排者记录 `ACCEPTED`。无法运行必要门禁、预算耗尽或需要新权限/范围时记录 `INCOMPLETE`，不得用继续等待或扩大任务伪装完成。

优先使用运行环境的持久记录；否则追加 `.scratch/afk-runs/<slug>.jsonl`。每个状态事件至少记录：切片与 attempt、agent、风险路由、请求 tier、按 `AGENTS.md` 解析出的运行配置、宿主实际采用的上下文隔离方式、固定点、持久任务机制、合同与候选指针、结果、证据增量、review 模式、blocker、返工次数、active/queue/tool/external elapsed，以及宿主可提供的 usage/cost。不可获得的字段写 `unknown`，不要省略。

事件区分 `DISPATCHED`、`READY_FOR_ACCEPTANCE`、`REVIEW`、`REWORK`、`DESIGN_EVENT`、`ACCEPTED` 与 `INCOMPLETE`。最终报告给出记录路径，并说明 Spec、ADR、设计文档和 `docs/observations/` 产物是否存在及是否被 Git 跟踪。

所有派发消息与最终产物遵循 `zh-first` 的语言与术语规则。
