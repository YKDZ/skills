# 实施约定

随用户启用的 `implement-spec` 使用。调度、分支、合并和 TDD 沿用上游；以下约定适用于本次工作的编排者、实施者和审查者。

## 派发与边界

- 派发者要求子代理读取本文件，并提供任务、原始需求、已有约定和证据的指针。子代理按职责执行；继续派发时，同样传递这些约定，包括审查子代理。
- 编排者派发前核对用户已确认的测试接缝，并把确认依据交给实施者。同一接缝内、已确认需求范围内的测试细化由实施者自行完成；缺失或真正变更的接缝由编排者统一向用户确认。
- 以用户确认的规格、任务单和既有项目规范为准。代理在这些边界内自行选择实施方法；既往设计、派发和审查意见不构成新增需求的授权。
- 继续工作需要尚未确定的用户取舍、补充授权或必要外部动作时，编排者及时说明所需决定及其影响，暂停依赖该输入的工作，继续其他独立工作。未确认的取舍保留为待决问题。
- 并行工作除工作树外，还须隔离会互相影响的服务、端口和测试状态，并明确资源清理责任。

## 持续实施

- 实施和修复子代理在开始前创建覆盖当前任务的 Goal。当前任务未完成时继续同一 Goal，结果与证据齐备后才结束；之后发现的修复工作另建 Goal。主代理不因本技能另建 Goal。宿主无法提供子代理 Goal 时交回编排者，不自行改为无 Goal 实施。
- 编排者确保调查、实施和审查结果落入既有任务单或接续材料，保存当前结果、有效证据、未决问题和下一步。证据注明对应版本与运行条件，相关材料使用指针；撤销的要求退出当前任务说明。
- 重复失败或长期不收敛时，编排者先核对历次派发、反例和关闭证据，查明共同原因，并检查现有要求和方案能否达成目标。再次派发前说明要查明或消除的原因；已有证据否定的路径只在相关事实变化后重试。

## 验收与修复

- 实施者逐项提供已确认要求的验证证据，覆盖约定的生产入口与运行条件。明确未执行、跳过或仍未证明的部分；测试通过和 Goal 完成不能单独作为验收结论。
- 编排者核对实施证据与必要检查。证据齐备、必要检查通过并完成整合后，下游可以继续；独立审查沿用上游的最终审查阶段。
- 新增验收工作前，编排者说明哪项已确认要求仍缺证据。复用仍适用的证据和现有工具；辅助验证变复杂时，先简化或替换验证方法。
- 审查者只读检查固定候选，一次完成分配范围的审查。必修问题须给出具体反例或因果证据，并关联原始需求、既有规范或交付正确性；偏好性重构和额外加固单列为可选建议。编排者核对依据后决定本轮修复范围。
- 修复者先查明原因，修复后验证原反例及受影响的正常行为。由独立审查者针对原问题和修复影响复核；只有新证据显示影响范围扩大时，才扩大检查。

## 结束与接续

已确认要求均有有效证据、必要检查通过、独立审查完成且本轮必修问题均已复核关闭、资源按约定保留或清理后，编排者用自然语言说明交付结果与证据位置，结束工作。

尚有授权范围内可推进的工作时继续。全部未完成工作都需要人类输入，或用户明确给出的预算到点时，保存证据与继续位置，再交回用户；不自行设置重试次数或默认期限。
