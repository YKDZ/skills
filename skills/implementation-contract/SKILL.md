# 实施约定

随用户启用的 `implement-spec` 使用。调度、分支、合并、测试驱动开发和最终审查沿用上游。

## 派发与边界

- 派发者要求子代理读取本文件，并提供任务、原始需求、已有约定和证据的指针。子代理按职责执行；继续派发时，同样传递这些约定，包括审查子代理。
- 派发者传递已有的测试接缝确认依据；同一接缝内、需求范围内的测试细化由实施者自行完成。缺失或真正变更的接缝由编排者统一向用户确认。
- 以用户确认的规格、任务单和既有项目规范为准。代理在这些边界内自行选择实施方法；既往设计、派发和审查意见不构成新增需求的授权。
- 继续工作需要尚未确定的用户取舍、补充授权或必要外部动作时，编排者及时说明所需决定及其影响，暂停依赖该输入的工作，继续其他独立工作。
- 并行工作除工作树外，还须隔离会互相影响的服务、端口和测试状态，并明确资源清理责任。

## 持续实施

- 宿主支持时，实施和修复子代理创建当前任务的 Goal（行动目标），未完成时继续同一目标；结束后发现的新修复另建目标。宿主不支持时，由编排者安排未完成任务的接续。主代理不因本技能另建目标。
- 编排者将影响后续工作的结论、证据、未决问题和下一步写入既有任务单或接续材料。证据注明版本与运行条件，用指针引用；撤销的要求从当前任务说明中移除。
- 重复失败或长期不收敛时，编排者先核对历次派发、反例和关闭证据，查明共同原因，并检查现有要求和方案能否达成目标。再次派发前说明要查明或消除的原因；已有证据否定的路径只在相关事实变化后重试。

## 验收与修复

- 实施者提供覆盖已确认要求的验证证据，使用约定的生产入口与运行条件。明确未执行、跳过或仍未证明的部分；测试通过和 Goal 完成不能单独作为验收结论。
- 新增验收工作前，编排者说明哪项已确认要求仍缺证据。复用仍适用的证据和现有工具；辅助验证变复杂时，先简化或替换验证方法。
- 审查者只读检查固定候选。必修问题须给出具体反例或因果证据，并关联原始需求、既有规范或交付正确性；偏好性重构和额外加固单列为可选建议。编排者核对依据后决定本轮修复范围。
- 修复者先查明原因，验证原反例及受影响的正常行为。编排者核对证据；修复影响较大或现有验证不足以判断时，安排独立审查者复核原问题及修复影响。

## 结束与接续

编排者确认要求均有有效证据、必要检查通过、本轮必修问题已关闭后，按上游流程收尾，说明结果与证据位置，并按约定保留或清理资源。

尚有授权范围内可推进的工作时继续。全部未完成工作都需要人类输入，或用户明确给出的预算到点时，保存证据与继续位置，再交回用户；不自行设置重试次数或默认期限。
