# 反馈循环优化

目标是降低 **总等待 = 每轮延迟 × 轮数**。agent 场景下轮数被放大：一次修改就要跑一轮检查，单轮省下的一分钟在 30 轮里就是半小时。

以下内容只是启发式的，仓库标准、工具能力可以覆盖或跳过某条。

## 过程

1. **盘点**：列出本地检查命令（fmt、lint、typecheck、test、e2e 等）与 CI 的 job / step（安装、缓存恢复、下载、构建、测试等），记录每项耗时、输出体量，以及它们在一轮任务 / 一次推送中的运行次数
2. **按总成本排序**：成本 = 耗时 × 每轮次数 × 轮数，优先处理最大项。不要优化 3 秒的循环，除非它每轮跑 20 次
3. **只应用有证据的启发式**：从下面的基线中选取能消除已测量瓶颈的条目，一次最多改一两处，避免叠加后无法归因
4. **验证并回滚**：修改前后各测一次并保留数字；没有可测量的改进就撤销改动

## 启发式基线

每条都是"是什么 -> 怎么修"。

- **输出噪声** — 成功也刷日志、失败贴原始 dump -> 成功静默、失败才输出；`--quiet` / `--list-different` / `--pretty false` / `--output-logs=errors-only` 这类只报错误的形态优先
- **全量习惯** — 任何改动都跑全量套件 -> 高频循环只跑受影响范围（`--changedSince`、`--affected`、`-x/--lf` 等）；affected 判定失败必须回退全量，防假绿
- **冷启动与缓存缺失** — 每次检查从零开始、结果每轮重来 -> 常驻 watch / daemon / 语言服务；本地增量缓存（`eslint --cache`、sccache、Turbo / Nx）+ CI 远程缓存，键 = 平台 + lockfile hash，restore-keys 回退，setup-* 内置优先；大文件下载 / 传输（依赖、工具链、浏览器、fixtures 等）另设缓存，避免每轮重新拉取
- **失败淹没** — 存量错误与新增错误混在一起 -> delta 语义：只报新错误，预存债务不阻塞本轮
- **超时缺失或拍脑袋** — 不设超时（GitHub Actions 默认 360 分钟）或凭感觉设 -> 显式设超时并从历史分布校准，短超时 + 重试；e2e 用条件轮询不用固定 sleep。判断：超时不可能完美（慢与挂无法区分），但必须显式、有依据
- **静默挂起** — 长时间无输出，无法区分"还在跑"与"已死" -> 分钟级长任务输出心跳 / 阶段 checkpoint
- **重试无护栏** — 同一失败无限重试，或环境问题被当代码问题 -> 错误归一化后连续 3 次相同即暂停；任务设最大自动修复次数
- **串行与等尾** — 独立检查串行跑，或并行后仍等最慢分片 -> 并行化 + fail-fast（矩阵默认开，别关）+ deadline / 重试
- **缓存污染** — 低信任来源能写缓存，或缓存里塞敏感信息 -> 缓存只由可信触发写入，PR 只读；不缓存密钥
- **本地 / CI 双路径** — 本地与 CI 各一套入口与环境，出现"本地过 CI 挂"或反之 -> 同一入口（package.json scripts 等，不叠包装）+ 同一环境（锁文件、容器镜像、工具链配置进仓库）；CI 只加环境步骤，是最终可复现性门禁，本地先跑相同根 check。判断：完全统一不可能，但入口、依赖、环境必须统一

## CI 专项

- 依赖与构建缓存优先；工具链版本（actions `uses`、Node、包管理器、Rust 等）用 Dependabot 一类的自动更新覆盖
- 最快 gate 在前快速失败；慢 gate 并行或分片；产物与缓存保留期设短
- 每个 job / step 显式设 `timeout-minutes`

## 反模式

- 为每轮只跑几次的秒级命令加远程缓存 - 复杂度超过收益
- 用 hook 在每次编辑时跑全量套件 - 会显著拖慢会话，只挂快速、scoped 的检查
- 只优化单次运行时间而不优化轮数 - 提示与上下文质量往往贡献更大
- 把慢 e2e 当高频 gate 每轮都跑 - e2e 慢且易 flaky，只做低频收尾验证
