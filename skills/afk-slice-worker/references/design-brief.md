# C 类设计文档契约

只在被派发 C 类设计切片时读取。设计文档服务于一个共享机制，可被多个任务单引用；不要按任务单复制相同内容。

## 必须产出

1. **决策与范围**：要关闭的生产语义、适用任务单、权威来源和非目标
2. **选定机制**：关键组件、所有权、资源生命周期、状态转移、接口与数据契约
3. **失败模式**：可达输入、并发、重入、部分失败、崩溃窗口、重试、恢复、权限和外部依赖；只覆盖当前范围可触发的路径
4. **不变量**：每条使用可判断的陈述，并说明在何处维护
5. **证明方式**：每个关键不变量对应生产接缝、反例、测试判定机制或运行期观测
6. **假设与证据**：环境假设引用 `OBS-NNNN`；尚未验证的假设显式标记
7. **方案取舍**：选定方案为何足够；拒绝方案及拒绝原因。只记录会影响后续实现的选择
8. **实施边界**：实施者可自行决定的可逆细节，以及不得重新决定的单向门
9. **未决问题**：负责人和最小验证动作。会迫使实施者发明生产语义的问题存在时，设计状态为 `INCOMPLETE`

## 原型类型

- `logic`：验证状态、数据或机制语义；必须有单一可证伪假设
- `ui-feasibility`：验证数据、交互状态、路由或布局约束是否客观可行；必须有单一可证伪假设，不生成供偏好选择的方案集
- `ui-visual-options`：生成供人比较的视觉方案；必须由用户、任务单或规格明确要求，只能由人类选择

## 原型契约

只有派发消息明确允许原型时才填写，并在调用 `prototype` 技能前记录：

```text
PROTOTYPE-ID / 类型 / 授权来源 / 切片固定点 /
logic|ui-feasibility：单一可证伪假设 / 静态证据为何不足 /
  反证观察与判定阈值 / 将解锁的设计决策 /
ui-visual-options：人类选择问题 / 方案范围 / 运行与比较指引 /
允许操作与可写范围 / 探索预算（状态、动作、实验或方案数量） /
派发消息给出的可选停止条件 /
一次性工作树 / 一次性分支 /
临时文件、数据库、进程、端口与任务运行器入口 /
保留模式：ephemeral|reviewable / 清理负责人 / 清理触发条件 /
结果：supported|refuted|inconclusive|awaiting-human / OBS 指针 /
设计决策回填 / 清理证据
```

一次设计切片最多执行一个原型。探索预算必须在执行前给出有限范围，不能只写时间。首次获得决定性观察即停止；探索预算用尽、越过范围、结果不确定或出现第二个待验证假设时报告 `INCOMPLETE`，不得扩大实验。派发消息另有停止条件时照其执行；到点不代表假设被推翻。`ui-visual-options` 完成后报告 `READY_FOR_HUMAN`，不得由代理生成设计结论。

## 原型生命周期

1. 执行前记录正式工作树的状态，从切片固定点创建独立的一次性工作树和分支。原型文件、路由、依赖和任务运行器改动只能存在于该工作树
2. AFK 设计切片不得执行上游 `prototype` 中“折入真实代码”的动作。验证后的逻辑、组件或获选方案只形成设计决定，正式代码留给实施执行者
3. `logic`/`ui-feasibility` 的结论、复验命令和必要证据进入 `docs/observations/`，设计文档引用 OBS。`ui-visual-options` 的方案源留在 `reviewable` 分支与人类交接中，人类选择及理由写回设计文档；未决偏好不写成事实
4. `ephemeral` 是 `logic`/`ui-feasibility` 的默认模式。结论形成后停止进程、释放端口，清理临时数据库/文件和临时入口；确认一次性工作树没有来源不明的修改后，移除当前运行创建的工作树与分支
5. `reviewable` 只在明确需要人类操作时使用。把原型稳定在一次性分支，记录启动方式与工作树；停止无需持续运行的进程，报告 `READY_FOR_HUMAN`。人类决定写回设计后，另派清理动作移除已登记资源
6. 清理不得使用强制删除掩盖来源不明的文件或提交。目标与当前运行记录不一致时停止并报告 `INCOMPLETE`
7. 清理后比较正式工作树的前后状态；除设计文档和允许的 `docs/observations/` 外必须一致。差异、残留工作树/分支、临时资源或无法证明的清理均阻止 `READY_FOR_ACCEPTANCE`

## 约束

- 不为规格没有的需求设计，不进行投机性泛化或预留抽象
- 能用现有模式和因果测试关闭的问题不升级为 C
- `logic`/`ui-feasibility` 原型只用于契约中的单一假设；`ui-visual-options` 只用于形成一个明确的人类选择问题
- 原型代码不进入产品；人类选择的界面方案和验证后的逻辑也必须由后续实施执行者正式实现
- 文档应足以让 t1 实施者在不发明所有权、状态或失败语义的情况下开始工作；不是逐文件施工说明

完成时给出 `READY_FOR_ACCEPTANCE`、`READY_FOR_HUMAN` 或 `INCOMPLETE`，并列出每个未决假设、保留资源与清理状态。
