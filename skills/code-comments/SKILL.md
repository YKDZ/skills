# 代码注释

在当前任务范围内维护代码说明，帮助读者定位、调用和修改代码。优先用命名和结构表达意图，仍有信息缺口时再补充注释，无需为每个声明添加说明。

## 原则

- **接口优先**：优先检查模块对外提供的接口，让调用者无需阅读实现就能正确使用。补充名称和类型未说清的约定，如业务含义、前置条件、副作用或失败后的状态。
- **结构化说明**：模块与接口文档写在对应声明处，采用项目语言和工具链支持的格式，如 TSDoc、Javadoc。摘要要简短，按需使用标签，避免重复类型签名或机械填写空泛说明。
- **便于检索**：在负责相应功能的入口自然使用项目统一的领域术语，让读者能用需求中的词找到实现。避免堆叠关键词或到处重复同一段说明。
- **实现理由**：实现注释优先解释为什么这样做、需要保留哪些约束，避免复述代码已说清的操作。局部理由用普通注释写在相关代码旁；无法确认的设计理由不写成事实。
- **自包含**：必要约定和实现理由直接写在源码中，让读者无需依赖代码外的文档，尤其是未纳入版本管理的资料。共同约定集中写在权威接口处，各实现通过引用代码符号或继承文档复用，只补充自身特有的信息。
- **随代码更新**：行为变化时同步修正受影响的注释，删除已确认失真或冗余的说明。注释的价值在于是否提供必要信息，不以数量或覆盖率衡量；日常改动不扩展为全仓补注释。
