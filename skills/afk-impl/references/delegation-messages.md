# Subagent 消息构造参考

以下内容是按需增删的启发式资产，无需严格填写。

## 共同原则

一条消息应让接收者无需继承完整会话也能回答六个问题：

1. 要产生什么可观察结果？
2. 哪个实际边界必须成立：源码、进程、真实认证、候选产物、发布产物还是外部系统？
3. 哪些行为或性质不能被破坏？
4. 哪些相邻工作明确不属于本任务？
5. 哪个测试应先失败，且失败原因如何证明它命中了需求中的因果机制？
6. 哪些证据齐全才可报告完成？缺证据时如何报告？

优先给出 ticket / Spec、相关文件与可运行入口的位置，让 subagent 自己读原始材料。不转述整段历史，不把上一个 agent 的结论当事实。消息中的任务上下文应是**最小**充分集。

满足边界并给出证据时报告 `COMPLETE`；否则报告 `INCOMPLETE`、已完成部分、缺失证据与最小下一步。不得一边列出影响正确性的未验证项，一边宣称完成。

## Goal 护栏

Goal 属于各自 thread，父 agent 的 goal 不自动约束 subagent。仅当有界任务预计跨多个 turn、包含多项完成证据且可在当前权限内持续推进时，才在派发消息中要求 subagent 立即创建 goal，并把结果、约束与验证条件写进 objective；用户未明确要求时不设 token_budget。实施、包含多条发现的返工与大型最终审计通常适用；单 turn 小任务或可能立即依赖外部输入的任务不适用。

Goal 仍为 active 时，即使 subagent 生成 final，运行时也会自动发起 continuation 并保留 objective。只有直接证据齐全后才标记 complete；遇到阻塞先穷尽安全替代方案，只在满足 goal 工具的阻塞条件时标记 blocked。

Goal 只防止仍为 active 的任务自然停止，不能防止 subagent 错误地把任务标记完成，也不能替代清晰消息、因果测试与独立 review。

可在实施或返工消息中加一句：`该任务预计跨多个 turn；立即为上述有界结果创建 goal，验证条件未全部满足前保持 active。`

## 实施者

实施消息通常包含：

- 结果：一两句话描述用户最终能观察到的行为。
- 原始依据：ticket、Spec、ADR 或代码入口；优先级冲突时指明以哪个为准。
- 生产边界：什么不能用 mock、源码构建或普通轮询代替。
- 不变量与非目标：只列容易误改或容易扩张的部分。
- TDD 判据：先写会因缺少目标行为而失败的测试。
- 完成证据：针对性测试、必要的更宽门限，以及边界特有证据。

示例形态：

```text
实现 <ticket> 的一个纵向切片：<可观察结果>。

先读：<原始需求>、<相关入口>。不要依赖前一位 agent 的完成结论。
必须证明的边界：<例如由指定 commit 构建的 Candidate，而非工作区源码>。
保持：<不变量>。
不做：<相邻但不属于本切片的工作>。

测试优先：先添加一个在当前实现上因 <缺失机制> 而失败的测试，记录 RED；
再做最小实现并记录 GREEN。重构检查留给 /code-review，不在实现中扩大范围。
测试必须在删除/绕过 <目标机制> 时失败，不能只等待最终状态偶然出现。

只有 <证据清单> 全部成立才报告 COMPLETE；否则报告 INCOMPLETE 和最小阻塞点。
```

## 同一实施者的继续消息

复用已有上下文时，只派发下一个原子目标：指出当前缺口、允许修改的边界、预期新增的 RED 与完成证据。不重复发送整份 Spec，不把多个未完成切片一次塞给同一 subagent。

```text
继续当前工作，只处理 <一个缺口>。
当前证据表明 <可复现事实>；不要重复 <已完成探索>。
先让 <回归测试> 因该缺口失败，再修复并运行 <门限>。
完成协议仍为 COMPLETE/INCOMPLETE；不要扩大到 <非目标>。
```

## 返工者

返工消息发送原始需求与审计者的具体发现，不发送审计者的笼统结论。每个发现都要求：先复现或用测试证明缺口，再做最小修复，最后验证原边界，而不只是让新增断言变绿。

```text
返工 <范围>，解决以下发现：<逐条事实与要求>。

对每条发现：
1. 先建立能在当前代码上失败的因果回归测试，或说明为何必须用其他证据复现；
2. 做最小修复，不改变 <不变量/非目标>；
3. 运行针对性测试和 <生产边界门限>；
4. 逐条给出关闭证据。

若任一发现未关闭或边界门限无法执行，报告 INCOMPLETE，不宣称返工完成。
```
